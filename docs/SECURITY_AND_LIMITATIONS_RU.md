# Безопасность и ограничения

## 1. Текущий уровень безопасности

Версия 0.1.1 является локальной исследовательской лабораторией. Реальные ордера не отправляются. Это наиболее важное ограничение и одновременно защитный барьер.

## 2. Что уже защищено

- интерфейс по умолчанию слушает `127.0.0.1`;
- отсутствует live order router;
- отсутствует хранение API secret;
- независимый risk manager;
- kill switch по дневному убытку и просадке;
- stale-data и data-quality блокировки;
- ограничение спреда, confidence и net edge;
- ограничение размера и числа позиций;
- cooldown и loss streak pause;
- атомарное сохранение paper state;
- audit trail в SQLite;
- локальные автоматические тесты.

## 3. Чего нет

- аутентификации HTTP API;
- TLS;
- CSRF-защиты;
- разграничения пользователей;
- secret manager;
- live reconciliation;
- sandbox торговых ключей;
- подписания релизов;
- dependency lock с hash;
- изоляции процесса модели;
- промышленного мониторинга/alerting.

Поэтому сервер нельзя публиковать в интернет.

## 4. Финансовые ограничения

Программа не подтверждает прибыльность. Результат может быть искажён:

- переобучением;
- look-ahead ошибкой в будущих изменениях;
- selection bias;
- слишком короткой историей;
- неучтённым режимом рынка;
- приблизительной L2-очередью;
- оптимистичной latency;
- изменением комиссий;
- отсутствием partial fill;
- отсутствием реального exchange rejection;
- survivorship и symbol bias.

## 5. Ограничения L2

Публичный market-by-price стакан показывает агрегированный объём уровня, но не идентификаторы заявок. Нельзя точно восстановить:

- время каждой заявки;
- точную очередь;
- собственное место после amend/cancel;
- скрытые заявки;
- внутренние matching правила.

`queue_factor` — сценарное приближение.

## 6. Ограничение атомарного limit fill

После прохождения модельной очереди оставшийся объём исполняется целиком. Это избегает небезопасной half-position логики MVP, но не имитирует реальные частичные исполнения.

## 7. Ограничение обучения

- один символ;
- горизонт 12 событий;
- split 70/15/15;
- нет полноценного walk-forward orchestrator;
- нет purge/embargo;
- нет автоматического regime-balanced sampling;
- нет online learning;
- нет calibration report.

## 8. Ограничение backtest

- решения каждые 500 мс;
- live runtime решения примерно каждую секунду;
- историческая stale check отключена;
- simulator реагирует на записанные события, но ваши виртуальные заявки не влияют на рынок;
- нет market impact;
- нет funding/mark/liquidation mechanics позиции;
- нет portfolio/multi-symbol риска.

## 9. Ограничение интерфейса

UI предназначен для одного локального оператора. Не считайте его административной системой для команды без backend auth и базы пользователей.

## 10. Безопасность checkpoint

PyTorch checkpoint может быть опасным при загрузке из неизвестного источника. Используйте только собственные или проверенные файлы. В будущем предпочтительны безопасные форматы весов и строгая проверка схемы.

## 11. Supply-chain

Перед релизом:

- проверяйте зависимости;
- фиксируйте версии;
- запускайте security audit;
- не устанавливайте случайные форки;
- храните checksum артефакта;
- подписывайте релиз.

## 12. Будущие API keys

Когда появится testnet/live:

- отдельный subaccount;
- запрет withdrawal;
- IP whitelist;
- минимальные права;
- secret только в OS keyring/secret manager;
- никогда не в Git, frontend, log или screenshot;
- ротация после подозрения на утечку.

## 13. Перед первым testnet

Обязательны:

- unit/integration tests executor;
- idempotency;
- reconciliation при старте;
- unknown order state;
- reconnect user stream;
- emergency cancel all;
- emergency flatten;
- hard server-side notional cap;
- fail-closed при несовпадении локальной и биржевой позиции.

## 14. Перед минимальным live

Дополнительно:

- длительный shadow/paper период;
- измеренная фактическая latency;
- сравнение ожидаемых и фактических fills;
- stress на комиссии ×1.5, slippage ×2, latency +100/+250 мс;
- независимый просмотр кода;
- небольшой капитал, потеря которого допустима;
- ручное аварийное отключение.

## 15. Ответственное использование

Не увеличивайте плечо или риск, чтобы «исправить» слабую стратегию. Отрицательный edge не превращается в положительный от увеличения размера.
