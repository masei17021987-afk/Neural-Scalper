# Рыночные данные

## 1. Источники

Версия 0.1.1 поддерживает два источника.

### SyntheticMarket

Локальный генератор создаёт двухсторонний стакан и меняет рыночные режимы. Seed по умолчанию равен 42, поэтому эксперименты воспроизводимы при одинаковых настройках.

### Binance USD-M Futures

Публичный collector использует:

```text
REST  /fapi/v1/depth
WS    <symbol>@depth@100ms или 250ms
WS    <symbol>@aggTrade
WS    <symbol>@forceOrder
```

Торговые ключи не используются. Collector не имеет функций создания, изменения или отмены реального ордера.

## 2. Зачем нужен локальный стакан

WebSocket depth-событие обычно содержит только изменения, а не всю книгу. Поэтому программа:

1. подключается к combined stream;
2. буферизует события;
3. загружает REST snapshot глубиной до 1 000 уровней;
4. устанавливает `lastUpdateId`;
5. применяет буфер, который соединяется со snapshot;
6. проверяет дальнейшую последовательность;
7. создаёт BookSnapshot нужной глубины.

Если цепочка нарушена, `OrderBookGap` приводит к переподключению и полному восстановлению.

## 3. Проверка последовательности

Для первого diff требуется, чтобы ожидаемый идентификатор находился внутри диапазона `U..u`.

Для последующих futures-событий при наличии `pu` проверяется:

```text
pu == previous last_update_id
```

Если `pu` отсутствует, контролируется отсутствие большого пропуска между `U` и ожидаемым идентификатором.

События, у которых `u <= last_update_id`, считаются устаревшими и не применяются.

## 4. Представление стакана

Внутри `LocalOrderBook` стороны хранятся как:

```python
bids: dict[price, quantity]
asks: dict[price, quantity]
```

Количество `0` удаляет уровень. После обновления книга обрезается до `max_levels`.

В `BookSnapshot` попадают:

- symbol;
- exchange timestamp;
- local receive timestamp;
- sequence;
- список bid;
- список ask;
- последняя сделка;
- признак aggressor side через `buyer_is_maker`;
- последнее событие ликвидации.

## 5. Временные метки

Каждый snapshot содержит два времени:

### `exchange_ts_ms`

Время события, сообщённое биржей.

### `local_ts_ms`

Время приёма сообщения локальной программой.

Оценка задержки:

```text
latency_ms = max(0, local_ts_ms - exchange_ts_ms)
```

Это не чистая сетевой round-trip latency. Показатель включает разницу часов, путь сообщения и локальную обработку. Для точного исследования нужна синхронизация системного времени.

## 6. Сделки

`aggTrade` обновляет:

- price;
- quantity;
- buyer_is_maker;
- trade timestamp.

В feature engine сделка получает знак:

```text
buyer_is_maker = false → агрессивная покупка → положительный объём
buyer_is_maker = true  → агрессивная продажа → отрицательный объём
```

Одна и та же последняя сделка не добавляется повторно: контролируется timestamp.

## 7. Ликвидации

`forceOrder` преобразуется в:

- side;
- notional = |price × quantity|;
- exchange timestamp.

Feature engine хранит события в окне 10 секунд и рассчитывает нормированное давление покупок/продаж.

Ликвидация не является самостоятельным сигналом входа. Она используется вместе с реакцией стакана и потоком сделок.

## 8. Контроль качества данных

`DataQualityMonitor` работает fail-closed.

Проверки:

### Отсутствие одной стороны

Если нет bid или ask, score получает полный штраф.

### Crossed book

Если `best_bid >= best_ask`, книга считается повреждённой.

### Невозрастающая sequence

Повтор или движение назад снижает score.

### Подозрительно большой sequence jump

Разрыв более 100 000 идентификаторов отмечается как подозрительный.

### Устаревшее событие

Если `local_ts_ms - exchange_ts_ms > stale_after_ms`, повышается счётчик stale events и снижается score.

### Ценовой выброс

Переход mid более чем на 250 б.п. между соседними snapshot отмечается как outlier.

### Итог

```text
score = clamp(1 - сумма штрафов, 0, 1)
healthy = score >= 0.55
```

Даже если сигнал и риск прошли, runtime блокирует новую заявку, когда `healthy=false`.

## 9. Запись данных

`EventRecorder` открывает отдельный gzip-файл на каждый UTC-час.

Путь:

```text
var/data/records/<SYMBOL>/
```

Файлы:

```text
book_YYYYMMDD_HH.jsonl.gz
features_YYYYMMDD_HH.jsonl.gz
```

Каждая строка является самостоятельным JSON-объектом. Формат append-only облегчает восстановление после сбоя и потоковую обработку.

Компрессия gzip использует уровень 5 — компромисс между скоростью и размером.

## 10. Что записывается

### Book

Полный BookSnapshot в пределах настроенной глубины.

### Features

- names;
- values;
- regime;
- metadata;
- обе временные метки.

LOB tensor отдельно в features-файл не записывается. При обучении он заново строится из последовательности book snapshot.

## 11. Оценка дискового пространства

Точный объём зависит от:

- символа;
- частоты depth;
- числа уровней;
- рыночной активности;
- gzip-сжимаемости;
- включённой записи book/features.

Практический способ оценки:

1. записать один полный час;
2. сложить размеры `book` и `features`;
3. умножить на 24 и нужное число дней;
4. добавить 30–50% запаса;
5. повторить оценку в период высокой активности.

Команда PowerShell:

```powershell
Get-ChildItem .\var\data\records\BTCUSDT -File |
  Measure-Object Length -Sum
```

## 12. Целостность записи

Recorder делает `flush()` после каждой строки. Это снижает объём потерянных данных при аварии, но увеличивает дисковые операции.

При нормальной остановке все gzip handles закрываются.

Повреждённая последняя gzip-запись не должна автоматически считаться пригодной для обучения. Перед крупным обучением рекомендуется выполнить отдельную проверку файлов.

## 13. Recorded dataset

Тренировщик ищет:

```text
var/data/records/**/book_*.jsonl.gz
var/data/records/**/book_*.jsonl
```

Затем оставляет только snapshot, у которых `snapshot.symbol == config.market.symbol`.

Минимальная внутренняя проверка требует более `horizon + 100` валидных последовательностей после прогрева. Это технический минимум, а не достаточный объём для устойчивой модели.

## 14. Изменение символа

Символ нормализуется:

- переводится в верхний регистр;
- удаляются все символы, кроме букв и цифр;
- пустое значение заменяется на `BTCUSDT`.

После изменения symbol работающий источник нужно перезапустить.

## 15. Ограничения текущего collector

- один символ;
- один exchange;
- нет mark price, open interest, funding и basis;
- нет market-by-order идентификаторов заявок;
- нет точной биржевой queue position;
- raw WebSocket events не сохраняются текущим runtime, хотя recorder поддерживает `write_raw`;
- нет автоматического контроля свободного диска;
- нет ротации по размеру;
- нет удалённого хранилища.

Эти ограничения должны быть устранены до масштабирования на десятки инструментов.
